# Prerequisites and credentials

[Back to installation](../README.md#install-via-helm-recommended)

Prepare these items before installing the project charts. Commands use the `SRE_*` variables defined in the README. Run them from the repository root. Changes to an existing Traefik configuration can roll its pods; schedule that change appropriately.

## 1. Official Kubernetes integration

In SUSE Observability, open **StackPacks / Integrations → Kubernetes** and create one integration per cluster. Install the official Agent using the Helm command and values generated by your instance. Repeat for the Harvester Kubernetes cluster and each guest Kubernetes cluster.

Use the actual integration name as `clusterName` in this project's telemetry values. This label connects metrics with the corresponding Kubernetes topology.

```bash
helm list --kubeconfig "$SRE_CLUSTER_KCFG" --kube-context "$SRE_CLUSTER_CTX" --all-namespaces
kubectl get daemonset,deployment,pods \
  --kubeconfig "$SRE_CLUSTER_KCFG" --context "$SRE_CLUSTER_CTX" \
  --namespace "$SRE_AGENT_NS"
```

Check Agent coverage on control-plane and etcd nodes. If taints prevent scheduling, merge [the tolerations fragment](../integrations/agent-coverage/control-plane-values.yaml) into the **official Agent's values**, preserving existing settings, and upgrade its existing release with the same chart version. Do not deploy a second official Agent to fix missing coverage.

The telemetry chart reuses an ingestion Secret in its namespace. Check only the key names, without printing secret values:

```bash
kubectl get secret suse-observability-agent-secrets \
  --kubeconfig "$SRE_CLUSTER_KCFG" --context "$SRE_CLUSTER_CTX" \
  --namespace "$SRE_AGENT_NS" \
  -o go-template='{{range $k,$v := .data}}{{printf "%s\n" $k}}{{end}}'
```

Set `remoteWrite.existingSecret` and `remoteWrite.secretKey` to your actual names. The templates expect `suse-observability-agent-secrets` / `STS_API_KEY`. An existing valid ingestion key can be reused; it is not a dashboard-management token.

Official reference: [Kubernetes integration](https://documentation.suse.com/cloudnative/suse-observability/latest/en/k8s-getting-started.html).

## 2. Host and etcd collection

The node collector requires Linux, host networking and read-only access to host `/proc`, `/sys` and filesystems. Confirm that the namespace's admission policy permits the chart's DaemonSets. Review node selectors and tolerations in [telemetry values](../charts/sre-platform-telemetry/values.yaml).

For RKE2, the etcd collector runs only on nodes matching `etcd.nodeSelector` and scrapes `http://127.0.0.1:2381/metrics` using host networking. Verify the local listener on **each etcd member**:

```bash
curl --fail --silent --show-error http://127.0.0.1:2381/metrics \
  --output /tmp/etcd-metrics-check.txt
```

Run that check in the node's OS shell. If it fails, inspect the etcd pod arguments, listener and node role before changing RKE2. This path does not need the etcd client port 2379, an external metrics port or copied etcd private keys. `etcd-expose-metrics` is not required when the local listener is already available.

Set `etcd.enabled: false` for managed control planes where members are inaccessible. An exclusively mTLS metrics endpoint requires an extension to this collector configuration; do not disable etcd authentication to fit this template.

Leave `nodeExporter.pressureEnabled: false` until `/proc/pressure/io` and `/proc/pressure/memory` exist on all selected nodes. PSI is optional; ordinary CPU, memory and disk collection still works without it.

## 3. Traefik metrics in Rancher-managed RKE2

This has two parts: **Traefik produces the metrics**, and this project's telemetry chart collects them. Enabling only `traefik.enabled` in the collector does not configure Traefik itself.

Inspect the installed chart and workload:

```bash
kubectl get helmchart,helmchartconfig \
  --kubeconfig "$SRE_CLUSTER_KCFG" --context "$SRE_CLUSTER_CTX" \
  --namespace kube-system
kubectl get daemonset,deployment,pods \
  --kubeconfig "$SRE_CLUSTER_KCFG" --context "$SRE_CLUSTER_CTX" \
  --namespace kube-system --selector app.kubernetes.io/name=rke2-traefik
```

For a cluster provisioned by Rancher, open **Cluster Management → your cluster → Edit Config → Edit as YAML**. Merge this fragment into the existing configuration, preserving other settings:

```yaml
spec:
  rkeConfig:
    chartValues:
      rke2-traefik:
        metrics:
          prometheus:
            entryPoint: metrics
            addEntryPointsLabels: true
            addServicesLabels: true
        ports:
          metrics:
            port: 9100
            expose:
              default: false
```

Save and wait for reconciliation. The same fragment is available in [rancher-cluster-fragment.yaml](../integrations/rke2/rancher-cluster-fragment.yaml). Imported clusters and Rancher's local cluster may not have `spec.rkeConfig`; use their actual configuration owner instead.

### RKE2 managed directly

Keep a `HelmChartConfig` in the RKE2 servers' persistent manifests or the GitOps source that owns it:

```yaml
apiVersion: helm.cattle.io/v1
kind: HelmChartConfig
metadata:
  name: rke2-traefik
  namespace: kube-system
spec:
  valuesContent: |-
    metrics:
      prometheus:
        entryPoint: metrics
        addEntryPointsLabels: true
        addServicesLabels: true
    ports:
      metrics:
        port: 9100
        expose:
          default: false
```

Merge into the existing resource rather than creating a competing definition. For an existing `HelmChartConfig`, this helper backs up its values, merges the fragment and performs a server-side dry run without applying it:

```bash
mkdir -p "$HOME/suse-observability-config-backup"
chmod 700 "$HOME/suse-observability-config-backup"
python3 scripts/merge-traefik-values.py \
  --kubeconfig "$SRE_CLUSTER_KCFG" --context "$SRE_CLUSTER_CTX" \
  --overlay integrations/rke2/traefik-values.yaml \
  --backup-dir "$HOME/suse-observability-config-backup" \
  --output "$HOME/suse-observability-config-backup/rke2-traefik-config.yaml"
```

Review the output and update the source file that already owns the resource. On directly managed RKE2 this is commonly under `/var/lib/rancher/rke2/server/manifests/`. Keep server sources consistent. Editing only the live object can be reverted by its controller. See [RKE2 Helm](https://docs.rke2.io/helm/).

### Network access and supported routing

The collector needs internal TCP access to Traefik's metrics port, normally 9100. Do not expose it publicly. The telemetry chart creates an internal Service; pod annotations are not needed for this scrape.

If an existing NetworkPolicy isolates Traefik while already allowing web traffic, `traefik.allowMetricsNetworkPolicy: true` adds a restricted metrics allowance. Leave it false if no isolation exists: adding a pod-selecting policy can change previously open ingress behavior.

Backend inventory supports HTTP Kubernetes `Ingress` resources, including named service ports. `IngressRoute`, Gateway API and other providers require mapping changes. Certificate and open-connection panels remain cluster-wide even when an application is selected.

## 4. Private certificate authorities

Obtain the public CA certificate from the service administrator and verify its origin. A CA certificate is not the server's private key.

For remote write, create the CA Secret in each collector namespace:

```bash
kubectl create secret generic suse-receiver-ca \
  --kubeconfig "$SRE_CLUSTER_KCFG" --context "$SRE_CLUSTER_CTX" \
  --namespace "$SRE_AGENT_NS" --from-file=ca.crt=/PATH/receiver-ca.pem
```

Then add to that cluster's values:

```yaml
remoteWrite:
  caSecret: suse-receiver-ca
  caKey: ca.crt
```

For publishing Jobs, create the CA Secret in the central namespace and set `runner.caSecret` / `runner.caKey` in **both** publishing values files. For KubeVirt, follow [its separate CA procedure](KUBEVIRT.md). Keep TLS verification enabled.

## Publishing credentials

Publishing Secrets are required so Helm Jobs can authenticate to the SUSE management API. They are **not credentials created only for an assistant or browser session**. A manual CLI workflow still needs SUSE authentication but does not need the Job's Kubernetes Secret.

| Credential | Used by | Purpose |
| --- | --- | --- |
| SUSE ingestion API key | Agent, vmagent, KubeVirt collector | Send telemetry |
| SUSE dashboard service token | Dashboard publishing Job | Manage dashboards |
| SUSE monitor service token | Monitor publishing Job | Manage monitors |
| Kubernetes ServiceAccount | Ingress inventory sidecar | Read Ingress resources |
| Your kubeconfig | Helm and kubectl on your workstation | Install Kubernetes resources |

Sign in to the `sts` CLI with an administrative account using the instructions in your own SUSE instance. Confirm your context points to the intended instance. The administrator prepares roles and service tokens; the charts do not grant themselves permissions.

### Create dedicated roles

For a new instance, create these subjects and permissions. If they already exist, inspect them instead of recreating them:

```bash
sts rbac create-subject --subject sre-dashboard-publisher
sts rbac grant --subject sre-dashboard-publisher --permission get-dashboards
sts rbac grant --subject sre-dashboard-publisher --permission create-dashboards
sts rbac grant --subject sre-dashboard-publisher --permission update-dashboards
sts rbac grant --subject sre-dashboard-publisher --permission delete-dashboards
sts rbac describe-permissions --subject sre-dashboard-publisher

sts rbac create-subject --subject sre-monitor-publisher
sts rbac grant --subject sre-monitor-publisher --permission get-monitors
sts rbac grant --subject sre-monitor-publisher --permission create-monitors
sts rbac grant --subject sre-monitor-publisher --permission update-monitors
sts rbac grant --subject sre-monitor-publisher --permission delete-monitors
sts rbac describe-permissions --subject sre-monitor-publisher
```

These are system-level permissions, not an access restriction to this repository's object names. The publisher code limits the objects it manages. The tested monitor import API requires all three write permissions together, including `delete-monitors`, even though the monitor Job performs no deletions. It does not require `get-settings` or `update-settings`.

Confirm the permissions exposed by your server with `sts rbac list-permissions`. See [official RBAC roles](https://documentation.suse.com/external-tree/en-us/cloudnative/suse-observability/latest/en/setup/security/rbac/rbac_roles.html).

### Create service tokens and Kubernetes Secrets

Make sure the central namespace already exists. Choose an expiration date according to your organization's policy. The following Bash block creates tokens without putting their values in shell arguments or printing them:

```bash
umask 077
SRE_TOKEN_DIR="$(mktemp -d)"
trap 'rm -rf "$SRE_TOKEN_DIR"' EXIT
read -r -p "Token expiration (YYYY-MM-DD): " SRE_TOKEN_EXPIRATION

sts service-token create --name sre-dashboard-helm \
  --roles sre-dashboard-publisher --expiration "$SRE_TOKEN_EXPIRATION" \
  --output json > "$SRE_TOKEN_DIR/dashboards.json"
sts service-token create --name sre-monitor-helm \
  --roles sre-monitor-publisher --expiration "$SRE_TOKEN_EXPIRATION" \
  --output json > "$SRE_TOKEN_DIR/monitors.json"

python3 - "$SRE_TOKEN_DIR" <<'PY'
import json, sys
from pathlib import Path
directory = Path(sys.argv[1])
for name in ("dashboards", "monitors"):
    response = json.loads((directory / f"{name}.json").read_text())
    (directory / f"{name}.token").write_text(response["service-token"]["token"])
PY

kubectl create secret generic suse-observability-dashboard-token \
  --kubeconfig "$SRE_CENTRAL_KCFG" --context "$SRE_CENTRAL_CTX" \
  --namespace "$SRE_CENTRAL_NS" \
  --from-file=serviceToken="$SRE_TOKEN_DIR/dashboards.token"
kubectl create secret generic suse-observability-monitor-token \
  --kubeconfig "$SRE_CENTRAL_KCFG" --context "$SRE_CENTRAL_CTX" \
  --namespace "$SRE_CENTRAL_NS" \
  --from-file=serviceToken="$SRE_TOKEN_DIR/monitors.token"

rm -rf "$SRE_TOKEN_DIR"
trap - EXIT
unset SRE_TOKEN_DIR SRE_TOKEN_EXPIRATION
```

The block is for initial creation. Reuse valid Secrets on subsequent Helm upgrades. For rotation or external secret management, follow your organization's procedure. Save the tokens to your approved vault before removing temporary files if recovery is required. Never commit them.
