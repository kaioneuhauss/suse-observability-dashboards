# Prerequisites by environment

Complete only the sections for the collectors you intend to use. Then return to [chart installation](../README.md#3-install-the-charts). These charts extend an existing installation; they do not install SUSE Observability, Traefik, etcd or the official Agent.

## Workstation and all targets

1. Install [kubectl](https://kubernetes.io/docs/tasks/tools/) and [Helm](https://helm.sh/docs/intro/install/). Both Helm 3.19 and 4.1 were checked for this package.
2. Obtain a kubeconfig and context for each target. Set `KCFG`, `CTX`, `AGENT_NS` and `CONTENT_NS` as shown in the README. Check existing releases before installing another collector.
3. Confirm DNS, trusted TLS and outbound access to SUSE and the configured image registries. The publisher also downloads its pinned CLI by HTTPS; [restricted-network preparation](../docs/details/DEPLOYMENT-REFERENCE.md#10-segurança-atualização-e-aceite) explains the custom-image option.

```bash
kubectl get nodes --kubeconfig "$KCFG" --context "$CTX"
helm list --all-namespaces --kubeconfig "$KCFG" --kube-context "$CTX"
```

## SUSE Observability: central server

1. Install and size the server using the [official requirements](https://documentation.suse.com/cloudnative/suse-observability/latest/en/setup/install-stackstate/requirements.html).
2. Add each Kubernetes integration in SUSE and use its generated official Agent installation instructions. Confirm the cluster appears and has current topology/metrics.
3. Complete [publisher access](PUBLISHER.md): one existing default role, one Service Token, one Kubernetes Secret for a new installation. Dedicated roles are optional.
4. For KubeVirt, enable the OpenTelemetry StackPack and provide a reachable OTLP gRPC TLS endpoint. If it already exists, reuse it. Otherwise edit [otlp-ingress-values.yaml](otlp-ingress-values.yaml): hostname, ingress class, TLS Secret, actual receiver Service and port. Merge it with the **complete existing server values**, keeping the installed chart version and release name. This can reconcile server workloads and belongs in the server's change process. See the [official OTLP ingress procedure](https://documentation.suse.com/cloudnative/suse-observability/latest/en/setup/install-stackstate/kubernetes_opentelemetry_ingress.html).
5. Configure global SMTP if using email. Notification rules are created manually after the chart publishes the monitors.

The remote-write URL usually ends with `/receiver/prometheus/api/v1/write`. Use the endpoint of your own instance; see [SUSE Prometheus remote write](https://documentation.suse.com/cloudnative/suse-observability/latest/en/use/metrics/k8s-prometheus-remote-write.html). The OTLP profile uses `hostname:443`, without `https://` or a path.

## Every monitored cluster: official Agent

Install the Agent using the instructions generated by its SUSE Kubernetes integration. For an existing Agent, reuse it. In the chosen Agent namespace, check:

```bash
kubectl get pods --kubeconfig "$KCFG" --context "$CTX" -n "$AGENT_NS"
kubectl get configmap suse-observability-agent-cluster-name \
  --kubeconfig "$KCFG" --context "$CTX" -n "$AGENT_NS" \
  -o jsonpath='{.data.STS_CLUSTER_NAME}{"\n"}'
kubectl get secret suse-observability-agent-secrets \
  --kubeconfig "$KCFG" --context "$CTX" -n "$AGENT_NS"
```

Use the returned integration name as `clusterName`. Check that the Secret has key `STS_API_KEY` without printing its value. If your Agent uses different object names or credential storage, set the collector values to an approved intake Secret in the same namespace. The package does not copy Secrets between namespaces.

## RKE2 with Traefik

1. Confirm that this cluster actually runs Traefik. Harvester with NGINX skips this section.
2. For Rancher-provisioned RKE2: open **Cluster Management → cluster → Edit Config → Edit as YAML**. Merge [rancher-rke2-traefik.yaml](rancher-rke2-traefik.yaml) into `spec.rkeConfig.chartValues.rke2-traefik`.
3. For local/imported RKE2: edit the persistent configuration that owns `HelmChartConfig/rke2-traefik` in `kube-system`. Merge [rke2-traefik-values.yaml](rke2-traefik-values.yaml) into `spec.valuesContent`; preserve existing values. Do not manage the same configuration through two sources. [RKE2 Helm documentation](https://docs.rke2.io/helm).

Required values inside the existing Traefik chart configuration:

```yaml
metrics:
  prometheus:
    entryPoint: metrics
    addEntryPointsLabels: true
    addServicesLabels: true
ports:
  metrics:
    port: 9100
    expose:
      default: false
```

4. Wait for its rollout and confirm metrics are available on every Traefik Pod. Changing this configuration may restart ingress Pods; plan accordingly.
5. If NetworkPolicies already isolate Traefik, permit collection on internal port 9100. The chart's opt-in policy requires both `traefik.allowMetricsNetworkPolicy: true` and `traefik.existingIsolationConfirmed: true`. Review existing web/websecure and egress rules first: adding the first ingress policy can block other traffic. Keep these fields false otherwise.
6. Set `traefik.enabled: true` in your platform values. After installation, run the [Helm connectivity test](../docs/VALIDATION.md). Do not expose metrics publicly.

## RKE2 or Harvester: etcd

The collector reads the local metrics endpoint on etcd nodes; it does not access the client API on 2379.

1. List the etcd nodes and check the selector used by your distribution:

```bash
kubectl get nodes --kubeconfig "$KCFG" --context "$CTX" \
  -l node-role.kubernetes.io/etcd=true
```

2. On each etcd node, using your approved SSH access, run:

```bash
curl --fail --max-time 5 http://127.0.0.1:2381/metrics
```

3. Confirm etcd metric families are returned. Then set `etcd.enabled: true`; customize `etcd.endpoint` and `etcd.nodeSelector` only when the verified environment differs.

The tested RKE2 clusters already exposed this endpoint on loopback. No `etcd-expose-metrics` change was needed. Do not turn that option on just to follow this package; it concerns metrics on the client interface. If the local endpoint is absent, leave collection disabled and check your version's [RKE2 configuration](https://docs.rke2.io/reference/server_config). A single-member cluster has no peer RTT observations; that does not imply a broken collector.

## Harvester: VM metrics

1. Install/reuse the official Agent. Follow the [Harvester version-specific procedure](https://docs.harvesterhci.io/v1.8/advanced/addons/suse-observability-agent/); the v1.8 add-on is documented as Experimental. Choose the customer's supported deployment method. Do not install a second Agent over an add-on.
2. Complete the central OTLP prerequisite above. Confirm the intake credential is authorized for that receiver.
3. Set `KCFG`, `CTX`, `AGENT_NS` to Harvester. Copy its **public KubeVirt CA** to the collector namespace:

```bash
mkdir -p local/ca
kubectl get configmap kubevirt-ca \
  --kubeconfig "$KCFG" --context "$CTX" -n harvester-system \
  -o jsonpath='{.data.ca-bundle}' > local/ca/kubevirt-ca.crt
openssl x509 -in local/ca/kubevirt-ca.crt -noout -subject -dates
```

Confirm the file contains the expected CA before creating/updating the ConfigMap:

```bash
set -o pipefail
kubectl create configmap kubevirt-metrics-ca \
  --kubeconfig "$KCFG" --context "$CTX" -n "$AGENT_NS" \
  --from-file=ca-bundle=local/ca/kubevirt-ca.crt --dry-run=client -o yaml \
  | kubectl apply --kubeconfig "$KCFG" --context "$CTX" -f -
```

4. In Rancher/Harvester, create or reuse a registry credential Secret named `application-collection` in `AGENT_NS`, with access to `dp.apps.rancher.io`. Use the organization's Application Collection credentials. Confirm a real image pull at rollout; a Secret's existence is not a pull test.
5. Check `kubevirt-prometheus-metrics` and its ready endpoints in `harvester-system`. The chart's CA/server names must match the certificates served by your KubeVirt version. For x509 errors, check CA and SAN; keep verification enabled.
6. Edit `deploy/virtual-machines/values.yaml` through your local copy and install the VM chart. Use the same `clusterName` as the Harvester platform collector.

After KubeVirt CA rotation, refresh the copied ConfigMap, increment `kubevirt.ca.revision` and upgrade the collector. The copy does not rotate automatically. VM OS statistics depend on the guest's capabilities; see [metric interpretation](../docs/GUIA-ESTUDO.md).

## Applications

Traefik metrics work without adding application code. The **Instrumented apps** view needs compatible application HTTP metrics already collected by an Agent/OTel pipeline. Installing dashboards does not create application instrumentation. [Detailed metric sources and customization](../docs/details/IMPLEMENTATION.md) explain what to map for another application.
